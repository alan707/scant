## Primary user story

Someone -- at work or an open-source contributor -- hears about `scant`, wants to try it on a repo they already have checked out. `pip install scant` (or `pipx install scant`) from PyPI, no Rust toolchain needed (maturin-built wheels). They `cd` into the repo and run `scant` (no arguments needed). It should just work: detect whatever manifest format the repo uses, detect whatever Python environment they already have set up, and print the report. No flags required for the common case.

Confirmed via Astral's own docs: `ruff check` with no path argument checks the current directory. `scant`'s `path` argument is already positional with `default_value = "."` (same mechanism), so `scant` and `scant .` are already identical -- no separate flag needed for that part.

For "detect whatever Python environment they already have" to actually hold, `--python` auto-detection needs to check, in order: `$VIRTUAL_ENV` (an already-activated venv -- the most common real case for anyone with a dependency-heavy repo, which is exactly this tool's audience), `$CONDA_PREFIX` (an already-activated conda env, same site-packages layout as a venv once located), then `.venv`/`venv` directories under the scanned root (present-but-not-activated). A fourth tier -- falling back to whatever `python3`/`python` resolves to on `PATH` when none of the above are set, by locating its site-packages -- is explicitly **out of scope for this phase** (it's a genuinely hard, whole-subsystem problem; `uv` has dedicated interpreter-discovery machinery for exactly this). Named as a follow-up GH issue candidate ("robust Python interpreter discovery"), not silently skipped. If all three tiers miss, the friendly `--python`-needed error is the honest fallback, not a guess.

## Context

Phase 0 (merged) gave `scant` a fast walk+parse: `scant .` prints `scanned N files in <time>`. That was a stepping stone, not the product. The actual deliverable -- the thing the README already promises and the thing that differentiates `scant` from deptry/fawltydeps -- is the per-dependency report: for every dependency a project declares, how much it's actually used, and a verdict (`drop`/`inline`/`keep`).

This plan implements that: manifest parsing, RECORD-based name resolution, single-pass import/usage extraction, classification, and the flat report renderer already locked in README.md.

**Deliberate revision of PLAN.md's original Phase 1 scope:** PLAN.md as written staged manifest formats across phases -- Phase 1 = `pyproject.toml` only (mkdocs), Phase 2 = + `requirements.txt`/pip-compile detection (Superset/edx-platform), "later" = Poetry/`setup.cfg`/`setup.py`/`Pipfile` (§14, grouped with the Bazel adapter). Alan explicitly asked to pull `requirements.txt`, `setup.cfg`, and `setup.py` detection into this phase instead, reasoning that a huge share of the real-world, dependency-heavy, mature codebases this tool targets predate `pyproject.toml` and would otherwise be invisible to it. This is correct: `requirements.txt` is close to a hard requirement for real-world usefulness (it's the most common way deployed Python apps declare deps, which is exactly the "cruft-heavy" audience), and `setup.py`/`setup.cfg` are still common in pre-2021 codebases. `Pipfile` support is explicitly **out of scope** -- niche enough today (pipenv's mindshare has shrunk relative to poetry/pdm/uv) that it's deferred to a filed GH issue ("Need to support Pipfile") rather than built now. Bazel adapter stays deferred (Alan confirmed). **PLAN.md's own phase-boundary text (§13/§14) will need a follow-up edit to match once this plan is approved and implemented.**

Constraints that remain from PLAN.md's Phase 1 (unaffected by the scope pull-forward): RECORD-based name resolution via `--python` (no heuristic fallback yet), both signals at default thresholds, text output only, no excludes beyond the denylist, no JSON, no `[tool.scant]` config file, no caveat logic, no entry-point handling yet.

Acceptance (PLAN.md §13): reproduces the prototype's mkdocs result (3 barely-used: `colorama`, `markupsafe`, `mergedeep`), does NOT flag `pyyaml-env-tag` (proves RECORD resolution beats heuristic guessing), zero false positives, runs <1s, output matches an `insta` snapshot. New acceptance bar for the pulled-forward formats: hand-verify against at least one real `requirements.txt`-only repo and confirm pip-compile'd lockfiles are detected and not diffed as hand-written (the edx-platform trap PLAN.md's non-negotiable #5 describes), since that's the single most damaging failure mode this expansion introduces if done wrong.

This was designed with a Plan subagent that verified the exact `ruff_python_ast`/`ruff_python_parser` visitor API at the pinned tag (`0.16.2`) against live GitHub source, confirmed `pep508_rs` 0.9.2 as the current crates.io release, and fetched mkdocs' real `pyproject.toml` to ground the manifest design against real data (15 declared deps: 14 in `[project.dependencies]` + `babel` in `[project.optional-dependencies].i18n` -- matches PLAN.md §12's table). Follow-up research (this session) confirmed `pep508_rs::Requirement` natively parses PEP 508 direct-URL/`git+https://` forms (needed for `requirements.txt`), and identified `configparser` 3.2.0 (current crates.io release, `multiline = true` option) as the Rust crate for `setup.cfg`'s Python-`configparser`-style continuation-line values -- a real gotcha, since generic INI parsers don't handle indented multi-line `install_requires =` blocks by default.

## Key grounding facts

- mkdocs declares `colorama >=0.4; platform_system == 'Windows'` -- a marker-gated dependency that's still one of the 3 expected "barely-used" findings. **Markers must be parsed and discarded, never evaluated** -- a dependency is "declared" regardless of its marker.
- mkdocs' manifest already spells one entry `pyyaml_env_tag` (underscore). PEP 503 normalization must treat `pyyaml_env_tag` / `pyyaml-env-tag` / whatever the dist-info directory calls itself as identical.
- `pep508_rs::PackageName::new()` already does PEP 503 normalization (lowercase, collapse `-_.` runs to `-`) and `.as_dist_info_name()` gives the reverse (underscore-escaped, dist-info-directory form). **Use this on both the manifest side and the dist-info side instead of hand-rolling normalization** -- a genuine simplification vs. what PLAN.md §4 anticipated.
- `ruff_python_ast` 0.16.2's `walk_stmt` already recurses into every nested body (function defs, try/except handlers, if/elif/else, for/while/with). This means PLAN §11a's "lazy imports inside functions" and "conditional imports in try/except" test cases need **zero special-case code** -- a default recursive visitor handles them for free.
- `from x import *` has no special AST variant -- it's a normal `Alias` whose `name` is the literal string `"*"`.
- `Expr::Attribute`/`Expr::Name` both carry a public `range: TextRange` field. `ruff_text_size` is a separate crate (not re-exported by `ruff_python_ast`) and needs its own git-pinned workspace dependency entry, tag `0.16.2`, just to name `TextRange`.

No new crate needed for `setup.py`'s best-effort parsing -- it reuses `ruff_python_parser`/`ruff_python_ast`, already a dependency for scanning source files.

## New modules in `crates/scant-core/src/`

**`manifest/` (new directory, replaces the single-file `manifest.rs` from the original narrower plan)** -- a small dispatcher plus one submodule per format.

**Precedence, not union.** A project may have more than one manifest-shaped file (e.g. `pyproject.toml` for real direct deps *plus* a `requirements.txt` that's just `pip freeze` output for deployment pinning -- transitive-inclusive, no pip-compile header to flag it as a lockfile). Blindly merging every format found would silently re-introduce the exact edx-platform bug non-negotiable #5 exists to prevent: transitive packages read as "directly declared." So `manifest::load(root)` tries detectors **in priority order** -- `pyproject.toml` -> `setup.cfg` -> `setup.py` -> `requirements.txt` -- and uses the **first one that yields at least one dependency** as the sole authoritative source. It only falls through to the next detector if the current one doesn't exist or parses to zero dependencies. `requirements.txt`'s own pip-compile-lockfile detection (sibling `.in` / `# via` provenance) still applies whenever it ends up being the chosen source -- this matters because plenty of real projects (e.g. edx-platform) have *only* `requirements/*.txt`, no `pyproject.toml`/`setup.py` at all, and that file may itself be a compiled lockfile.

(`Pipfile` explicitly out of scope for this plan -- niche today, tracked as a new GH issue instead of built now.) Friendly `ManifestError::NotFound` (listing all four formats scant looks for, per CLAUDE.md's error-catalog style) only if none are found or all found files parse to zero dependencies; a found-but-broken file is `ManifestError::Malformed { path, message }` naming the specific file. `requirements.txt` discovery is root-level only for this phase (`<root>/requirements.txt`) -- not `requirements/*.txt` subdirectory layouts or `requirements-dev.txt`/multi-file setups. That's a known, named gap (edx-platform's real layout is `requirements/edx/base.txt`), left for a `--requirements <path>` override flag later rather than guessing which of several files is authoritative now.

- **`manifest/pyproject.rs`** -- `[project.dependencies]` + every group under `[project.optional-dependencies]` (PEP 621 only; no PEP 735 `[dependency-groups]` yet). Each raw requirement string goes through `pep508_rs::Requirement::from_str(..).name` -- never hand-split on version operators.
- **`manifest/requirements.rs`** -- parses `requirements.txt` (and any file it `-r`-includes, recursively, cycle-guarded). Per line: skip blank/comment lines; skip `-c constraints.txt` (constraints, not declarations); follow `-r other.txt` includes; `-e <path-or-url>` editable installs are still real declared deps (parse the trailing `#egg=name` or the PEP 508 form after stripping `-e`); everything else parsed via `pep508_rs::Requirement::from_str`, which natively handles PEP 508 direct-URL/`git+https://` forms (confirmed via docs.rs/GitHub -- no hand-rolled URL parsing needed). **Pip-compile detection (non-negotiable #5, the critical case):** if the file's header contains `# autogenerated by pip-compile` (or similar `pip-compile`-tool signature comment), treat it as a lockfile, not a hand-written manifest -- look for a sibling `.in` file with the same basename (`requirements.txt` -> `requirements.in`) and parse *that* as the authoritative direct-dependency source instead; if no sibling `.in` exists, fall back to per-entry `# via` annotation parsing (`# via -r foo.in` or no annotation = direct, `# via somepackage` = transitive, skip transitive entries so we never flag ~240 transitive deps as "unused" the way a naive diff would on edx-platform).
- **`manifest/setup_cfg.rs`** -- `[options] install_requires` (multi-line, one requirement per line) + `[options.extras_require]` (one multi-line block per extra name), via `configparser` with `multiline = true`. Purely declarative INI, no execution risk.
- **`manifest/setup_py.rs`** -- **best-effort only, never executes the file.** Parses via the existing `ruff_python_parser`, walks the AST (reusing the same `Visitor` infra as `parse.rs`) looking for a call whose callee is `setup` or `setuptools.setup`, with an `install_requires=` keyword argument. If that argument's value is a literal list/tuple of string literals, extract them as PEP 508 specs. If it's anything else (a variable, `open('requirements.txt').read().splitlines()`, a conditional expression -- all real, observed patterns), **skip that keyword gracefully and record a warning** (`"found setup.py but couldn't statically determine install_requires -- dependencies declared there may be missing from this report"`) rather than silently reporting zero/partial deps as if that were the whole truth. This warning-not-silent-gap behavior is the load-bearing safety property of this submodule.

`Pipfile` is intentionally not built in this plan -- to be filed as a new GH issue ("Need to support Pipfile") after this plan is approved, for a later phase.

**`namemap.rs`** -- given a resolved site-packages directory, reads every `*.dist-info/RECORD` (falling back to `top_level.txt`) to build `import root -> distribution` and `distribution -> {import roots}` maps. Distribution name for each `*.dist-info` dir comes from `PackageName::new()` on the dirname's `{name}` segment (split before `-{version}`), so it normalizes identically to the manifest side. `entry_points.txt` is explicitly untouched (Phase 2). Resolving the `--python` argument to an actual site-packages dir: if the path itself directly contains `*.dist-info` entries, use it as-is; else try `<path>/lib/python3.*/site-packages` (POSIX venv layout) then `<path>/Lib/site-packages` (Windows); else a friendly `NameMapError::NoSitePackages`. Bare interpreter-binary paths are an explicit, documented Phase 1 limitation (no `sysconfig` shell-out).

**`discover.rs`** (extend, don't replace) -- split the existing `scan()` into `walk(root) -> Vec<PathBuf>` (the existing denylist-pruned, `.py`-filtered walk, unchanged logic) and a new `first_party_packages(root) -> HashSet<String>` (top-level dirs directly under `root` containing `__init__.py` -- matches the validated prototype's algorithm exactly, non-recursive, `src/`-layout is a known accepted gap). First-party check runs *before* namemap lookup during import resolution, so a project's own top-level package name never gets mistaken for a same-named installed dependency.

**`parse.rs`** -- the core extraction. One `ruff_python_parser::parse_module` call per file, one `Visitor` walk over the resulting AST collecting both import bindings and usage sites (single-pass, per CLAUDE.md's performance rule). Key rules, each a real interpretation decision since PLAN.md doesn't specify this level of detail:
- Resolution key for both `import a.b.c` and `from a.b import c` is always the **root segment** (`a`) -- matches how RECORD's top-level import names work. Relative imports (`level > 0`) are always skipped, no resolution attempted.
- `imports` counts distinct import *statements* touching a dist, not aliases (`from x import a, b, c` is 1 import, up to 3 symbols).
- `from x import *`: no bindings created, dist recorded in a `wildcard_imported` set instead. `analyze.rs` forces `Verdict::Keep` for these regardless of other signal -- prevents a false "unused" flag from a construct we fundamentally can't attribute.
- Symbol for `from x import y` bindings is `y` itself. For `import x` (module bindings), symbol is the *first* attribute accessed off the bound name (`numpy.linalg.norm(...)` -> symbol `linalg`, not `norm`) -- falls out naturally from the visitor only matching `Attribute{value: Name(..), ..}` and recursing inward on deeper chains. A bare use with no attribute access (`cb = numpy`) counts toward `files`/`lines` but contributes no symbol -- chosen because it never under-counts usage (can't make something look *more* unused than it is).
- `files`/`lines` come strictly from actual `Name`/`Attribute` usage sites, **never** from the import statement's own line -- this is what makes the README's `numpy` example (`imports:1, files:1, lines:1`) self-consistent as "one import, one separate usage line."
- Known, accepted limitation: the binding map is flat and only mutated by import statements (never by ordinary assignment), so a local variable that happens to share an import's bound name (`numpy = 5` inside a function) isn't detected as shadowing. Same approximation the validated prototype made; real code essentially never does this.
- A file that fails to read or fails to parse is skipped with no entry (a warning, not an error, per CLAUDE.md -- one bad file doesn't stop the run).

**`analyze.rs`** -- orchestrates manifest + namemap + discover + parse (parse runs in parallel via `rayon`, same pattern as the existing `discover::scan`), aggregates per-file results into per-dependency `DepUsage { imports, files, lines, symbols }`, classifies:
- `imports == 0` -> `Verdict::Drop`
- below all three thresholds (`lines <= threshold_lines && files <= threshold_files && symbols <= threshold_symbols`) -> `usage: Trivial`, `Verdict::Inline`
- otherwise -> `Verdict::Keep`, with a display-only usage band (`Light`/`Moderate`/`Heavy`) computed from `lines` alone as multiples of `threshold_lines`: `<= 3x` -> Light, `<= 10x` -> Moderate, else Heavy. (Sanity-checked against the locked `requests` example: 287 lines / threshold 3 -> `287 > 30` -> Heavy, matches.) These multipliers have no PLAN.md backing -- they're my call, flagged here for visibility, purely cosmetic (never flips a verdict).
- `Verdict::MakeOptional` is **not emitted in Phase 1** -- PLAN.md names it in the vocabulary list but never defines a trigger condition anywhere. Deferring it to Phase 2 (where entry-point/extras awareness would make the distinction meaningful) and collapsing everything that would qualify into `Inline` for now.
- Deps sorted by normalized `PackageName` for deterministic output; displayed using the manifest's original spelling (`PyYAML`, not `pyyaml`).

**`report.rs`** -- renders the flat format already locked into README.md (per-dep block: `imports:`/`files:`/`lines:`/`usage:`/`verdict:`, 2-space indent, values column-aligned). `Drop`-verdict deps have no usage band to show -- prints `usage: none` for that line (needs a real mkdocs run to sanity-check the wording before locking the `insta` snapshot).

## CLI wiring (`crates/scant-cli/src/main.rs`)

Add `--python <PATH>` as **optional**, not required -- README already shows bare `scant .` as the primary usage example, so a hard requirement would break the published UX. Default behavior, per the primary user story above: check `$VIRTUAL_ENV`, then `$CONDA_PREFIX`, then `.venv`/`venv` under the scanned path, in that order; if none resolve and `--python` wasn't passed, print a friendly error (what happened / why / what to do next) and exit 2. This means Phase 1 hard-errors rather than degrading gracefully when no Python env is found at all (no active env, no local `.venv`), since both the heuristic-fallback resolution tier *and* system-`PATH`-interpreter discovery are out of scope for this phase -- noted so it's not mistaken for a regression later. Also flags a new, separate warning case worth handling here: if the resolved `--python` environment has zero (or near-zero) overlap with the declared dependency set -- i.e. the namemap doesn't recognize almost anything that's actually declared -- print a warning before the report ("None of your declared dependencies appear to be installed in `<path>` -- did you mean to install them first?") rather than silently letting an unpopulated/wrong venv produce a report where every dependency reads as `drop`. This is a real cold-start trap: a fresh clone before `pip install -r requirements.txt` would otherwise look like "100% of your dependencies are unused" on first run.

Also wires up `--threshold-lines`/`--threshold-files`/`--threshold-symbols` (defaults 3/2/1, already-named flags, not yet connected to anything real). Replaces the Phase 0 "scanned N files" placeholder output with `report::render()`. Exit code: 0 if every dep's verdict is `Keep`, 1 if anything is flagged `Drop`/`Inline`, 2 on the operational errors above -- matches PLAN.md's exit code contract.

## Testing

Unit tests (synthetic tempdir fixtures, no real venv/network) covering:
- `manifest/pyproject.rs`: plain deps, optional-dependency groups, marker-bearing requirement kept, malformed/missing file errors.
- `manifest/requirements.rs`: plain lines, blank/comment skipping, `-r` include (incl. a cyclic-include guard), `-c` constraint skipping, `-e` editable (path and `git+`/`#egg=` forms), pip-compile header detection with sibling `.in` preferred, pip-compile `# via` direct-vs-transitive classification when no `.in` sibling exists (the edx-platform trap -- this is the single most important test in the new scope).
- `manifest/setup_cfg.rs`: single-line and multi-line `install_requires`, multiple `[options.extras_require]` blocks, missing `[options]` section (no deps, not an error).
- `manifest/setup_py.rs`: literal `install_requires=[...]` list extracted correctly; `setuptools.setup(...)` (attribute-form call) recognized same as bare `setup(...)`; non-literal value (e.g. a variable or a file read) produces the graceful warning and zero extracted deps, never a crash or a silently-wrong empty-but-unflagged result.
- `manifest::load()` dispatcher: merge across two formats present simultaneously (e.g. `pyproject.toml` + legacy `setup.py`) dedupes correctly by normalized name; `ManifestError::NotFound` only fires when literally none of the four are present.
- `namemap.rs`: `Pillow`->`PIL`, `PyYAML`->`yaml`, `python-socketio`/`python_socketio` dash/underscore matching, `pywin32`->`win32api`, one dist owning multiple top-level import roots (`setuptools`/`pkg_resources`), `top_level.txt` fallback. Namespace-package disambiguation (`google-cloud-*` family) explicitly **not** implemented or asserted correct in Phase 1 -- structural-only test (doesn't panic), gap documented per PLAN §4/§11a.
- `parse.rs`: every import form from PLAN.md §11a -- `import a.b as c`, multiline `from x import (a,\n b)`, relative imports (skipped, no crash), `import *` (wildcard set, no bindings), try/except conditional import, lazy import inside a function, stdlib import (silently unresolved, no namemap entry needed), first-party import (skipped even if a same-named dist exists), multi-name `from x import a, b, c` (imports=1, symbols=2 if only 2 used), multi-dist `import x, y` in one statement, deep attribute chain symbol attribution, same-line double usage deduped by `BTreeSet`.
- `analyze.rs`: `classify()` truth table including the light/moderate/heavy boundaries, wildcard-import forced-Keep override, and a small synthetic end-to-end run reproducing the shape of the mkdocs case (drop / RECORD-only-resolvable / light / heavy) without needing real pip.
- `insta` snapshot on `report::render()`'s output against the synthetic fixture -- this is what satisfies "<1s, matches an insta snapshot" in fast, offline CI.
