# Build Plan: `scant` — a fast Python dependency usage analyzer

> **Name: `scant`** — "barely enough," which is exactly the signal this tool exists to find. Verified available on PyPI and crates.io. Repo: `github.com/alan707/scant`.

> **How to use this file with Claude Code:** work **phase by phase**. Each phase has explicit *Acceptance Criteria* that must pass before the next begins. Prefer the narrow, correct version over the broad, clever one.

> **Status:** the algorithm in this plan has been **prototyped in Python and validated against 8 real repositories** (see §14). The findings — including four classes of false positive discovered in the wild — are folded into the design below. `proto.py` ships alongside this plan as a test oracle.

---

## 1. Mission

`scant` scans a Python project and answers two questions in plain language:

1. **Unused** — which declared dependencies are never imported anywhere?
2. **Lightly used** — which dependencies are used so little (a couple of lines, one or two files, a single symbol) that you could probably inline the code and drop the dependency?

The *unused* check is well-trodden (deptry, fawltydeps, pip-check-reqs). The **lightly-used check is the differentiator** — no popular tool flags "you import one helper from this 100MB package." That feature is the reason this tool exists; protect it.

**Proof it works:** the prototype found that Apache Superset (74k stars) calls Facebook's `prophet` — one of the heaviest packages in the Python ecosystem — on **2 lines in 1 file**. That single finding is the product pitch.

**Non-goals (v1):** auto-removing deps, type checking, CVE scanning, license auditing, Python 2, conda.

---

## 2. Guiding principles (these win arguments)

1. **Beginner ergonomics first.** A first-time user runs `scant` with no arguments and gets a useful, beautiful answer. Zero required config.
2. **Fast by default, no tuning.** Sub-second on a medium repo. Speed is a feature users *feel*.
3. **Performance and friendliness must not trade against each other.** Do the expensive-but-kind work (verification passes, caveats) only on the small suspect set, never on the whole tree. See §7.
4. **Correct-by-default, never silently wrong.** If a choice could flip a verdict, say so out loud. Trust is the product.
5. **Plain language everywhere.** Readable by a Python user who has never written Rust and doesn't know what an AST is.
6. **Honest about limits.** Dynamic imports, namespace packages, entry points. Say so in docs and output.

## 3. Scope & boundaries

### Python version support: **3.9 → 3.14**
The tool is a Rust binary and is independent of the analyzed code's Python version, so supporting a wide range is cheap — *except in one place that matters*.

- **Parsing:** Python 3 syntax is essentially forward-compatible. A modern parser reads 3.9 code fine. Parse a superset of all 3.x syntax. Python 2 should fail to parse and be skipped with a friendly note (correct behavior, not a bug).
- **⚠️ The stdlib set SHRANK — this is the real work.** Ship a **version-keyed stdlib module table**, one set per version 3.9–3.14, generated from `sys.stdlib_module_names`.
  - 3.12 removed `distutils`, `imp`, `asynchat`, `asyncore`
  - 3.13 removed the PEP 594 "dead batteries": `telnetlib`, `cgi`, `crypt`, `nntplib`, and others
  - If you ship only 3.14's list, a 3.9 codebase importing `distutils` is misclassified as third-party and reported as an *undeclared dependency* — a false alarm on the first run.
- **`--target-version <3.9..3.14>`**, defaulting to: `requires-python` from the manifest → the resolved interpreter → newest.
- **`importlib.metadata.packages_distributions()` is 3.10+**, so for 3.9 environments read `.dist-info/RECORD` directly. Since RECORD-reading is the primary path anyway (§4), this costs nothing.
- Document that 3.9 is supported *because old codebases have the most cruft*, even though 3.9 itself is EOL (Oct 2025).

### Dependency-declaration inputs
- **Core:** `pyproject.toml` (PEP 621 `[project.dependencies]`, `[project.optional-dependencies]`, PEP 735 `[dependency-groups]`) and `requirements*.txt` + `requirements/*.txt`.
- **requirements.txt mechanics:** `-r` includes, `-e` editables, `-c` constraints, environment markers, `--hash=`, `git+https://…` URLs.
- **⚠️ CRITICAL: detect pip-compile output (the lockfile in disguise).** Validated on edx-platform: `requirements/edx/base.txt` has 301 entries and looks like a normal requirements file, but **~240 are transitive**. Diffing against it reports ~240 packages as "unused." Detection signals, both reliably present:
  - header comment `# autogenerated by pip-compile`
  - per-entry annotations: `# via -r requirements/edx/kernel.in` = **direct**; `# via somepackage` = **transitive**
  - **Behavior:** prefer the sibling `.in` file when one exists; otherwise recover the direct set from `# via` annotations; always explain the choice in output.
- **Never diff against** `poetry.lock`, `uv.lock`, `Pipfile.lock`, `pylock.toml` (PEP 751). They list *resolved transitive* deps. They may serve as a **cost input** for the weight score (§12 Phase 5) — never as the comparison target. Leave a code comment saying so, or a future contributor will "fix" it and reintroduce the bug.
- **Later adapters:** Poetry `[tool.poetry.dependencies]`, `setup.cfg`, `setup.py` (best-effort literals), `Pipfile`.
- **Out of scope:** conda `environment.yml`.

### Source inputs & exclusions
- Scan `.py`. `.pyi` stubs tracked separately (type-only, not runtime usage). `.ipynb` opt-in later.
- **Hard-exclude denylist (never scanned, silent):** `.venv`, `venv`, `site-packages`, `node_modules`, `build`, `dist`, `__pycache__`, `.git`, `.tox`, `.eggs`, `*.egg-info`. Scanning these reads a dependency's *own internal imports* as project usage — the most damaging bug class.
- Respect `.gitignore` by default (`--no-respect-gitignore` to opt out).
- **⚠️ Scan tests BY DEFAULT.** Validated on beets: excluding `test/` made `discogs-client` and `reflink` look unused when their only imports live there. Test-only usage is real usage of a real dependency. Users may exclude tests explicitly; the tool must not do it for them.

## 4. Name resolution (the heart of correctness)

**Distribution name ≠ import name.** `Pillow`→`PIL`, `PyYAML`→`yaml`, `beautifulsoup4`→`bs4`, `python-socketio`→`socketio`, `pywin32`→`win32api`. There is no rule; the mapping is *data* recorded at install time.

**Measured impact:** the heuristic-only path produced roughly a **20% false-positive rate** on unused findings across the validation repos. Metadata resolution is not a nicety — it is the difference between a trustworthy tool and a noisy one.

Resolution tiers, in priority order:

1. **Read installed metadata (primary, version-independent, no Python needed).** For each `*.dist-info/`:
   - `RECORD` — authoritative file manifest. Top-level import names = first path components that are a directory with `__init__.py` or a bare top-level `.py` (ignore `.dist-info`/`.data`).
   - `top_level.txt` — convenience list; fast path, fall back to RECORD.
   - **`entry_points.txt` — see below. Do not skip this.**
2. **`packages_distributions()` (3.10+)** if an interpreter is available — one shot-out, read JSON.
3. **Heuristic + curated overrides (approximate — label it).** PEP 503 normalize (lowercase, collapse `-_.` → `-`) then guess; override table for known offenders. Mark results lower-confidence.

### ⚠️ Entry-point dependencies (discovered on Superset — bigger than expected)
Superset produced **83 "unused"**, most of them false. It never imports `sqlalchemy-redshift`, `pydruid`, `snowflake-sqlalchemy`, or ~40 other database drivers — **SQLAlchemy loads them by connection string via setuptools entry points**. Same for `pytest`, `ruff`, `pre-commit`, `gunicorn` (run as commands).

In a real enterprise app, entry-point deps can *dominate* the unused list. A tool that says "delete your Redshift driver" gets uninstalled.

**Mitigation (first-class, Phase 2):** read `entry_points.txt` from each dist-info. Any package registering entry points — SQLAlchemy dialects, `pytest11` plugins, `console_scripts`, Flask/Django extensions — is **used-by-registration**, reported in its own low-key category, never as "unused."

### Other resolution edge cases
- **Namespace packages** (`google-cloud-storage` + `google-cloud-bigquery` under `google`): import→dist is one-to-many. Disambiguate on the second path component or by RECORD file matching, or you under-report.
- **One dist → many imports** (`setuptools` ships `setuptools` + `pkg_resources`). Import names are always a *set*.
- **Data-only packages** (`tzdata`, validated on pelican) — never imported by design.
- **Stub packages** (`types-*`, `*-stubs`) — never imported by design.
- **Transitive pins** (`numba`, `resampy` in beets) — declared in an extra purely to constrain a transitive of `librosa`. Genuinely unimported, but *intentional*. Explain rather than accuse.

## 5. Tech stack & the speed playbook

**Language: Rust.** Ship **Maturin-built wheels** so users `pip install scant` / `pipx install scant` with no Rust toolchain — the same friction-removal Ruff uses, essential for adoption.

| Concern | Choice | Notes |
|---|---|---|
| Parser | `ruff_python_parser` + `ruff_python_ast` (git pin) | Fastest available; real typed AST. Not published as a stable API — pin a revision, ride `main`. Fallbacks: `tree-sitter-python`, `rustpython-parser`. |
| File walking | `ignore` (ripgrep) | gitignore-aware, parallel, custom ignore filenames. |
| Parallelism | `rayon` | Embarrassingly parallel across files. |
| CLI | `clap` (derive) | Subcommands, help, env fallbacks. |
| TOML | `toml` | pyproject. |
| Requirement specs | `pep508_rs` (Astral) | Strips versions/extras/markers correctly — don't hand-roll. |
| Pretty errors | `miette` | Friendly annotated diagnostics. |
| Color | `anstream` + `owo-colors` | TTY detection, `NO_COLOR`. |
| Snapshots | `insta` | Locks the ASCII output. |
| CLI tests | `assert_cmd` + `trycmd` | Exit codes, golden runs. |
| Benchmarks | `criterion` + `hyperfine` | Regression gate. |

**Speed techniques from Ruff/ty:**
- **Single pass, shared structures.** Parse each file once; extract imports *and* usage sites in the same traversal. This is Ruff's core trick and the reason it runs 10–100× faster than the tools it replaces.
- **Parallelize across files** with `rayon`.
- **Arena-allocated AST** (the rustc/oxc technique: linear memory access, cheap drop). `ruff_python_ast` already does this — don't reinvent it.
- **Content-hash cache** (ESLint-style): hash file → cache its extracted import/usage set → skip unchanged files. ~50 lines, big win on CI re-runs.
- **Prune excluded dirs at the walk level** (`filter_entry`), never descend into `.venv`.
- **Skip Salsa in v1.** ty uses it for keystroke-level incremental recomputation — that pays off in a watch-mode/LSP, not a one-shot CLI that reads everything once. Revisit only for `--watch`.

**Perf target (measured baseline):** the Python prototype analyzed Superset (1,501 files) in **3.0s**. The Rust port should land at **0.1–0.2s**. Use Superset as the standing benchmark.

## 7. CLI design & ergonomics

### Reconciling speed with friendliness (principle §2.3)
The friendly features (verification, caveats, explanations) are **cheap because they run on the suspect set, not the tree**:
- Main pass: parse everything once, in parallel. This is the only full-tree work.
- Verification passes (excluded-path re-scan, entry-point lookup, pip-compile provenance) touch only the handful of deps already flagged — typically <20 of 165.
- Result: the kind, careful output costs milliseconds on top of the fast path.

### Command shape
```
scant [PATH]           # zero-config
scant explain <DEP>    # why is this flagged? where is it used?
```

### Flags
**Thresholds — "how little is too little?"**
- `--max-lines <N>` — used on N or fewer lines (default `3`)
- `--max-files <M>` — …and in M or fewer files (default `2`)
- `--max-symbols <K>` — …and K or fewer distinct symbols (default `1`)
- A dep is "lightly used" when below **all** active thresholds (AND, not OR — document this).

**Scanning:** `--exclude <GLOB>` (repeatable, gitignore syntax), `--exclude-from <FILE>`, `--extend-exclude <GLOB>` (adds to defaults instead of replacing), `--no-respect-gitignore`

**Resolution:** `--python <PATH>`, `--target-version <3.9..3.14>`, `--ignore-dependencies <NAME,…>`

**Output:** `--format <text|json|sarif>`, `--no-color`, `-q/--quiet`, `-v/--verbose`, `--version`, `--help`

### Config (`pyproject.toml`)
```toml
[tool.scant]
max-lines = 3
max-files = 2
max-symbols = 1
target-version = "3.11"
exclude = ["**/migrations/"]
ignore-dependencies = ["types-requests", "tzdata"]
python = ".venv"
```
**Precedence:** CLI > `pyproject.toml` > defaults.

### Exit codes
`0` clean · `1` findings (fails CI) · `2` operational error

### The exclude caveat
- Denylist paths: hard-pruned, silent.
- User excludes: default to "excluded = out of scope" for the verdict, **but** when an exclusion is the *sole* reason a dep reads unused/light, name the dep and files and downgrade confidence. Implement by re-scanning excluded paths **only for the already-suspect deps** (cheap).

## 9. Output design — beautiful ASCII

Light rules, generous spacing, plain language, no heavy box-drawing. Color additive, never load-bearing. **Real findings from Superset shown below.**

**Group by what to DO, not alphabetically.** At ~6 lines per dep, 165 deps = 1,000 lines and the one finding that matters (`prophet`) is buried at line 600. A tool that reports everything reports nothing. The default view triages; per-dependency detail lives in `scant explain`.

### Default report

```
  scant · superset                    165 deps · 1,501 files · 0.18s
  ──────────────────────────────────────────────────────────────────

  DROP?          never imported                              3
    bottleneck            0 files      0 lines
    polyline              0 files      0 lines
    mako                  0 files      0 lines

  INLINE?        one symbol, a few lines                    19
    prophet               1 file · 1 sym · 2 lines     heavy install
    hashids               1 file · 1 sym · 3 lines     tiny, pure python
    geopy                 1 file · 1 sym · 2 lines     heavy install
    holidays              1 file · 1 sym · 2 lines
    … 15 more

  REGISTERED     loaded via entry points, not imports       41
    sqlalchemy-redshift, pydruid, snowflake-sqlalchemy, … (-v to list)

  KEEP           earning their place                       102

  ──────────────────────────────────────────────────────────────────
  scant explain prophet
```

### Detail view (`scant explain <dep>`)

```
  scant explain prophet

    usage         trivial
    files         1     superset/utils/pandas_postprocessing/prophet.py
    symbols       1     Prophet
    lines         2     line 59, line 66
    declared      [project.dependencies]

    prophet pulls in cmdstanpy and a bundled Stan toolchain
    (~100 MB). You call one class on two lines.

    verdict       consider inlining or making optional
```

**Vocabulary rules:**
- Say **`usage`**, not "complexity" — we measure how much you lean on a library, not how complicated it is. Scale: `trivial / light / moderate / heavy`.
- **`lines`**, not "references" — count *distinct lines*, not occurrences. `foo(bar(x))` is one line, and "how much code would I rewrite" is the question users are actually asking.
- Lead with **symbols**, not import count. `from x import a, b, c` is one import but three symbols; "you use one function from this" is the pitch.
- Verdicts are concrete verbs: `drop`, `inline`, `make optional`, `keep` — never vague ones like "review".
- Section headers end in `?` where the tool is suggesting, not asserting (`DROP?`, `INLINE?`).

**Caveat block** (fires only when relevant):
```
  NOTE — 1 result depends on an excluded path
  'requests' looks unused, but its only imports are in paths you
  excluded (scripts/seed.py). If that code still ships, requests
  is NOT unused. Re-run without --exclude to confirm.
```

**pip-compile block:**
```
  NOTE — requirements/edx/base.txt is generated by pip-compile
  It lists 301 packages, but only ~61 are declared directly; the
  rest are pulled in automatically. scant read the direct ones
  from requirements/edx/kernel.in instead.
```

**Rules:** TTY detection; deterministic sort (category, then name) for stable snapshots; `--quiet` drops chrome; `sarif` enables GitHub code-scanning annotations.

## 10. Error handling — readable by non-developers

Every error: *what happened / why / what to do next*, in everyday words, via `miette`. **Never panic on user input.**

| Situation | ❌ Don't | ✅ Do |
|---|---|---|
| No manifest | `Error: ENOENT pyproject.toml` | `Couldn't find a dependency file here. scant looks for pyproject.toml or requirements.txt. Run it from your project's top folder, or pass the path: scant path/to/project` |
| Malformed pyproject | `toml parse error line 12 col 3` | `There's a formatting problem in pyproject.toml on line 12. Check that line for a missing '=' or quote.` |
| No venv | `packages_distributions unavailable` | `No installed environment found, so some package names can't be matched exactly (e.g. Pillow → PIL). Results are still useful but may miss a few. For exact results: scant --python .venv` |
| Permission denied | `EACCES: src/` | `scant couldn't read the folder 'src' (permission denied) and skipped it. Fix permissions, or exclude it: scant --exclude src/` |
| Python 2 file | stack trace | *(warning)* `Skipped 1 file scant couldn't parse (looks like Python 2): legacy/old.py` |

**Warnings vs errors:** one bad file is a *warning*, analysis continues. Only project-level problems (no manifest, bad config) are *errors* (exit 2).

## 11. Testing strategy

### 11a. Unit tests
- `namemap`: PEP 503 normalization; `Pillow→PIL`, `PyYAML→yaml`, `python-socketio→socketio`, `pywin32→win32api`, namespace `google`, multi-import `setuptools`.
- `manifest`: PEP 621, PEP 735, `-r`/`-e`/markers/URLs, **pip-compile detection + `# via` provenance**.
- `parse`: every import form — `import a.b as c`, multiline `from x import (a,\n b)`, relative, `import *`, conditional in try/except, **lazy imports inside functions**.
- `stdlib`: `distutils` is stdlib on 3.9–3.11 but third-party on 3.12+; `telnetlib` stdlib through 3.12, gone in 3.13.

### 11b. Fixture projects (`tests/fixtures/`) — one trait each
`unused/` · `light/` · `namespace/` · `name-mismatch/` · `stub/` · `entry-point/` · `pip-compiled/` · `excluded-usage/` (must trigger caveat) · `py39-distutils/` (version-sensitive stdlib)

### 11c. Golden real-world tests (the FP taxonomy, with real specimens)
Each of these was **observed in the wild** by the prototype and must be handled:

| Class | Specimen | Repo | Required behavior |
|---|---|---|---|
| Import-name mismatch | `pyyaml-env-tag`→`yaml_env_tag` | mkdocs | resolve via RECORD, don't flag |
| Import-name mismatch | `pywin32`→`win32api` | locust | resolve via RECORD |
| Entry-point registered | `sqlalchemy-redshift`, +40 | superset | separate category |
| Dev tooling | `pytest`, `ruff`, `pre-commit` | superset | separate category |
| Data-only package | `tzdata` | pelican | allowlist |
| Transitive pin | `numba`, `resampy` | beets | explain, don't accuse |
| Test-only usage | `discogs-client`, `reflink` | beets | scan tests by default |
| pip-compile lockfile | `base.txt` (301 → ~61 direct) | edx-platform | detect, use `.in` |

### 11d. Snapshot + CLI + bench
- `insta` snapshots on rendered text (locks the ASCII).
- `assert_cmd`/`trycmd` for exit codes, `--help`, JSON shape.
- `criterion` + `hyperfine`; **fail CI on >20% regression** against the Superset baseline.
- **Differential test vs `proto.py`** — run both on mkdocs and diff. The prototype's known-wrong outputs are documented expectations.
- CI matrix: `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` on Linux/macOS/Windows + maturin wheel build.

## 12. Validated target repositories

Chosen by **actually cloning and running the prototype** — not guesswork. All 10+ years old, all famous.

**Selection criterion: declared dependency count, age, and stars — NOT manifest format.** A 165-dep `pyproject.toml` and a 150-dep `requirements.txt` are the same problem; the tool parses both regardless. Format matters only for *parser correctness* (§3: requirements files may secretly be compiled lockfiles; pyproject `[project.dependencies]` is always hand-written), never for choosing a target repo. Pick repos for **cruft density**: many deps × long history × real application (not library).

## 13. Phased roadmap

### Phase 0 — Scaffold (½ day)
Workspace + two crates; CI green (fmt/clippy/test, 3 OSes); `clap` skeleton; `ignore` + `rayon` walk parsing every `.py` with `ruff_python_parser`, printing file count + time.
**Acceptance:** `scant .` prints `scanned N files in <time>`, exits 0. CI green.

### Phase 1 — mkdocs, end to end (THE narrow milestone)
Deliberately tiny: a *correct, beautiful report on one repo*, not generality.
**Constraints:** PEP 621 pyproject only. Import extraction, RECORD-based resolution via `--python`, both signals at default thresholds, text output only. No excludes beyond the denylist, no JSON, no config file, no caveat logic, no entry-point handling yet.
**Acceptance:**
- Reproduces the prototype's mkdocs result: 3 barely-used (`colorama`, `markupsafe`, `mergedeep`).
- **Correctly does NOT flag `pyyaml-env-tag`** — proves RECORD resolution works where the heuristic failed.
- Every finding hand-verified; zero false positives.
- Runs in <1s; output matches an `insta` snapshot.

### Phase 2 — Superset: robustness, config, the FP taxonomy
Both manifest families; PEP 735; **entry-point detection**; **pip-compile detection**; full excludes + caveat pass; `[tool.scant]` config; configurable thresholds; `--target-version` + version-keyed stdlib; override table + heuristic fallback; data-only/stub allowlist; `--format json`; friendly error catalog; `explain` subcommand.
**Acceptance:**
- All §11c specimens handled correctly.
- **Superset's 83 "unused" collapses to a small verified list**, with ~41 correctly reclassified as *registered, not imported*.
- The 19 barely-used findings reproduce, `prophet` among them.
- Fixture suite green including caveat + py39-stdlib.

### Phase 3 — Scale & speed (edx-platform)
> *Why this repo:* 4,417 files and ~150 direct deps make it the scale test. Its lower star count (~7k) is acceptable because it serves as a **correctness fixture** for compiled manifests, not a marketing showcase — Superset is the showcase. If a higher-profile scale target is wanted, evaluate **Apache Airflow** (~40k stars, ~12y, notoriously dependency-heavy, now pyproject) as an addition or substitute.

Content-hash cache; parallelism tuning; `criterion`/`hyperfine` in CI with regression gate; `--format sarif`; GitHub Action + pre-commit hook.
**Acceptance:** edx-platform (4,417 files, pip-compile requirements) analyzed correctly and fast; `base.txt` handled via `kernel.in`; cached re-run dramatically faster; CI fails on >20% regression.

### Phase 4 — Polish & adapters

### Phase 5 — The Weight Score (value-density) — *later / aspirational*
Reframes the tool from *deficiency detector* to **value-density map**: of all the weight you carry, how much pulls its weight? Subsumes both existing signals and adds the **cost** dimension that says *which* light deps are worth removing.

`worth ≈ benefit ÷ cost`:
- **Benefit** — *not* "what fraction of the API do you use" (using little of `requests` is correct; nobody should use more to raise a score). Instead: **code saved** (how much dep code does the work behind your calls — proxy: size of modules containing reached symbols; ambitious: call-graph reachability); **irreplaceability** (crypto/numerics/async/parsers are worth it at any usage; pure-Python convenience helpers are inlineable); **intensity** (call sites, centrality — already computed).
- **Cost** — install size (from RECORD); **transitive footprint** (closure from the lockfile — the heavyweight signal); maintenance surface (native extensions, staleness/libyear, bus factor).

```
              LOW cost (light)        HIGH cost (heavy)
            ┌───────────────────┬───────────────────┐
  HIGH use  │  earning its keep │  heavy but worth  │
            │   leave it alone  │  weight justified │
            ├───────────────────┼───────────────────┤
  LOW use   │ cheap convenience │    DEAD WEIGHT    │
            │  inline someday   │  ◄── biggest win  │
            └───────────────────┴───────────────────┘
```
Superset's `prophet` (2 lines, enormous install, pulls Stan) sits squarely bottom-right — the perfect demo. `hashids` (3 lines, tiny, pure Python) sits bottom-left: real but low priority.

**Repo headline:** *"412MB across 165 deps; 86% of that weight is well-used; 3 deps (14%) are dead weight."* Improves when you drop the right things, not when you use more API.

**Actionable:** estimate drop effort — *"`hashids`: 1 symbol, 3 lines, 0 transitive deps, pure Python → removing it ≈ 15 lines. Easy win."* vs *"`cryptography`: 4 symbols but reaches 2k lines of C-backed code → keep."*

**Stage it:** **5a** cheap signals only (symbols + install size + transitive count) → the 2×2, headline, drop-effort. **5b** (research-y, optional) reachability + irreplaceability model. 5b must not gate 5a.

**Guardrail:** never show a bare 0–100 score — it implies objectivity the heuristic lacks and invites gaming. Always show inputs: *"heavy: 25 transitive deps; barely used: 1 symbol, 2 lines."*
