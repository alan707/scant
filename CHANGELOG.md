# Changelog

All notable changes to `scant` are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [PEP 440](https://peps.python.org/pep-0440/).

## [Unreleased]

### Fixed
- Distributions shipping into a PEP 420 namespace package now resolve to their import names instead of none at all (#56). `read_record_full` accepted a RECORD path's first segment as an import root only when `site-packages/<segment>/__init__.py` existed, and a namespace root owns no `__init__.py` -- so `protobuf`, `opentelemetry-proto` and six `llama-index-*` packages resolved to nothing and were reported as `unknown`, "installed, but its import names couldn't be determined". A dependency scant cannot resolve is one it can never report on, so this was blindness rather than a wrong verdict. Two halves, because either alone would be wrong: resolution now descends until it reaches the directory that actually owns an `__init__.py` and takes the dotted path to it (`google.protobuf`, not `google`, bounded at three levels -- the deepest real nesting is `llama_index.embeddings.huggingface`), and the parser matches the *longest* known root, so `from google.protobuf import json_format` credits protobuf while `from google.cloud import storage` in the same file does not. Attributing at the shared namespace root instead would have traded a missing name for a wrong one: protobuf would read as heavily used the moment anything touched `google.cloud`. Both halves derive from what is on disk, per non-negotiable #10.

## [0.0.1a6]

### Added
- A dependency that another *used* distribution declares behind an `extra ==` marker is now reported as `registered` rather than `drop`. Database drivers are the specimen: mlflow declares `psycopg2-binary`, `PyMySQL` and `pymssql`, imports none of them, and reaches all three through SQLAlchemy's built-in dialects by connection string -- the same failure mode as CLAUDE.md non-negotiable #4, arriving through a door entry points don't cover, since a DBAPI driver registers nothing. The evidence is already on disk: SQLAlchemy's own `METADATA` names each one (`psycopg2-binary; extra == "postgresql-psycopg2binary"`), so this needs no hardcoded list of drivers and generalizes for free to celery brokers, cachelib backends and any other opt-in backend. Two constraints keep it narrow: only requirements carrying an `extra ==` marker count, because a plain `Requires-Dist` is an ordinary transitive dependency and half of site-packages requires `requests`; and the provider must itself be imported by the project, so an optional extra of something nobody uses excuses nothing. As with entry points, this only ever overrides `drop` -- a package the project does import is still a fair `inline` candidate. `METADATA` is read only as far as the first blank line, since RFC 822 headers end there and the whole README follows.
- A dependency whose import root is named in a string literal is now reported as `registered` rather than `drop`. Django is the specimen: `INSTALLED_APPS`, `MIDDLEWARE` and `STORAGES` load apps and middleware by dotted string, so `django-prometheus` and `whitenoise` are never imported anywhere and read as unused -- following that advice breaks the app at startup. The report names the exact file and line (`named as a string in src/paperless/settings/__init__.py:129`) so the claim can be checked rather than taken. Three constraints keep it from suppressing genuine findings: roots are matched against the declared set *during* the parse walk rather than collected wholesale, so a project's tens of thousands of string literals never accumulate; only strings shaped like a module path count, which excludes prose and URLs (`"please install django_prometheus"` and `"https://requests.example.com/x"` both fail); and a string never contributes lines or symbols, so it can answer "is this loaded by name" without ever making a package look used. Verified against real clones of authentik and paperless-ngx, where `drop` falls from 7 to 3 and 11 to 6.
- `--safe-to-scan-site-packages`: reads the source of packages you already import to explain dependencies that look unused. Django's `django/db/backends/postgresql/base.py` does `import psycopg as Database` inside a try/except, and declares that relationship in no metadata anywhere -- so an unimported `psycopg` reads as dead when it is the live database driver. Off by default, because CLAUDE.md non-negotiable #1 forbids scanning site-packages: doing so risks reading a dependency's own internal imports as *project* usage. Nothing here does that -- a hit produces `registered` naming the provider's file and line (`imported by django/db/backends/postgresql/base.py:26`) and contributes no imports, lines or symbols to any usage total -- but that distinction is ours to argue and the user's to accept, so it is opt-in. Three limits keep the work proportionate: it runs only over dependencies already headed for `drop`, so a clean project pays nothing; it searches only inside distributions the project actually imports, without which it would excuse any package mentioned anywhere in site-packages; and a substring pre-filter decides which files are worth parsing while the finding always comes from a real parse, so a name in a comment or a string is never mistaken for an import. A per-repository `[tool.scant]` equivalent is still to come.

### Changed
- Evidence a package supplies about *itself* -- entry points, an installed command -- now outranks every other signal for an unimported dependency, while evidence supplied by something else -- an extra-gated requirement, a string literal -- ranks below `unknown`. Found by the change above: mlflow's `protobuf` moved from `unknown` to `registered, optional dependency of google-cloud-storage`, which is true but implies scant looked for imports and found none. In truth it never learned protobuf's import names (`google.protobuf` is a namespace package), so it had nothing to look for. A package's own declaration still wins outright, which is what keeps a binary-only distribution like `dumb-init` reported as `registered` instead of falling into `unknown`.

## [0.0.1a5]

### Added
- Entry-point detection: a dependency that registers entry points in its `entry_points.txt` (a SQLAlchemy dialect, a `pytest11` plugin, a `console_scripts` command) is loaded by name at runtime rather than imported, so zero imports is expected rather than suspicious. These are now reported in their own `registered` group with the loading mechanism named in the `WHERE` column, instead of being flagged `drop`. Registration only ever overrides `drop` -- a registered package that *is* imported is still a fair `inline` candidate. Registered dependencies are not findings, so they no longer force exit code 1. Verified against a real changedetection.io clone, where `pytest-flask`, `pytest-mock`, `pytest-xdist`, and `jsonschema` moved out of `drop`, and against a real Apache Superset clone with all 165 declared dependencies installed, where `drop` falls from 78 to 19 with 50 reclassified as `registered` -- 36 of them `sqlalchemy.dialects`, the case this feature exists for.
- Marker-aware `unknown` verdict: a dependency gated to another platform or Python version (e.g. Superset's `waitress; sys_platform == "win32"`) can never be installed into the environment being scanned, so its absence from site-packages is not evidence of anything. These are now reported as `unknown` with the marker itself as the stated reason, rather than counted as `drop`. PEP 508 markers were previously parsed and discarded; they are now kept on each declared dependency and evaluated against the **environment scant was pointed at**, not the host running it -- a 3.9 virtualenv inspected from a 3.13 machine has to judge `python_version < "3.10"` as that virtualenv sees it. Where there is no interpreter to ask (a bare site-packages directory), the result is treated as unknown and the verdict is left unchanged; scant never infers "cannot install" from a failure to check. As with registration, a false marker only ever overrides `drop` -- platform-guarded code that does import the package still classifies normally, and a registered dependency stays `registered`, since registration is positive evidence where a false marker is only the absence of it. `unknown` is not a finding and does not affect the exit code. Verified against a real Apache Superset clone, where `waitress` moves out of `drop` with `only installs when sys_platform == 'win32'` as its stated reason, and no other verdict changes.
- Installed commands are now read from `RECORD`, so a dependency that ships a prebuilt executable rather than declaring a `console_scripts` entry point is recognized as `registered` instead of `drop`. `entry_points.txt` records what a package *declares*; `RECORD` records what actually got *installed*, and maturin-built tools (`ruff`, `uv`) ship a binary with no `entry_points.txt` at all. The signal is a `RECORD` path escaping site-packages into `bin/` or `Scripts/` (e.g. `../../../bin/ruff`), matched on the directory rather than a fixed depth, since that varies by layout; identical under `pip` and `uv`. These paths were previously skipped outright, which was correct for collecting import roots -- they still never become one -- but discarded the only evidence such tools leave behind. A `.py` file installed into `bin/` does not count: those come from setup.py's legacy `scripts=` list and are usually a demo or helper (xlrd ships `runxlrd.py`), so treating them as commands would suppress genuine findings on evidence that doesn't support them.
- A dependency that resolves to nothing is now reported as `unknown` rather than `drop`. `drop` is the one destructive recommendation scant makes, so it now requires positive confirmation that the package is installed and unimported -- never merely that scant failed to find it. The stated reason distinguishes the three ways this happens: gated to another platform (`only installs when sys_platform == 'win32'`), genuinely absent (`declared, but not installed in this environment`), or present but opaque (`installed, but its import names couldn't be determined`) -- which covers both a metapackage that ships no modules and legacy `.egg-info` metadata scant cannot yet read (#40). `.egg-info` directories are now recognized as proof a package is installed, even though their contents are still not parsed.

### Changed
- The `ACTION` column is now sized to the widest verdict actually present rather than a fixed width, so reports without registered dependencies render exactly as before.

### Fixed
- Tests that mutate process-global environment variables (`PATH`, `VIRTUAL_ENV`, `CONDA_PREFIX`) now serialize on a shared lock. They ran in parallel threads inside one process, so one test could restore `PATH` while another still depended on it -- a latent race that surfaced as `format_ambiguous_error_suggests_system_python_when_present` failing on all three CI platforms while passing locally.

## [0.0.1a4]

### Added
- The not-found and ambiguous Python-environment errors now also check `$PATH` for a `python3`/`python` interpreter and, if found, list it as an explicit option (e.g. `scant . --env /usr/local/bin/python3`). Never used for auto-detection -- a system interpreter isn't tied to a specific project and could have unrelated packages installed -- but surfaced as a suggestion since installing straight into a container's system Python (no venv at all) is a common, real setup. Found via a real Apache Superset container run, where the ambiguous-env error listed two unrelated leftover venvs but gave no hint that the actual answer was the system Python.

## [0.0.1a3]

### Added
- ASCII-art logo and CI/PyPI-version/license status badges to `README.md`.

## [0.0.1a2]

### Added
- `--env` flag (replaces `--python`, kept as a backward-compatible alias): accepts a venv directory, a direct interpreter path, or a path found under `bin/`/`Scripts/`, resolved via a `sysconfig` subprocess call instead of guessing the `lib/pythonX.Y/site-packages` layout.
- Auto-detection now finds any `pyvenv.cfg`-marked directory (not just `.venv`/`venv`), and reports an explicit "ambiguous" outcome with a friendly, ASCII-tree formatted message when multiple candidates are found.

## [0.0.1a1]

### Fixed
- The cold-start warning ("did you mean to install them first?") now excludes `pip`/`setuptools`/`wheel` from its resolved-overlap check. Found against a real Apache Superset clone: Superset declares `pip` as one of its 165 dependencies, and every venv bundles `pip` by default, so that single incidental match silently defeated the warning and produced a confidently-wrong "all 165 dependencies unused" report instead of flagging the empty environment.

## [0.0.1a0]

First alpha. `scant` is a Rust CLI that scans a Python project and reports, per declared dependency, whether to **drop** it (never imported), **inline** it (used so little that carrying the dependency probably isn't worth it), or **keep** it.

### Added
- Manifest detection across `pyproject.toml`, `requirements.txt` (including pip-compile lockfile detection), `setup.cfg`, and `setup.py` (best-effort, static-only -- never executes the file).
- RECORD-based distribution-to-import-name resolution (e.g. `PyYAML` -> `yaml`, `pyyaml-env-tag` -> `yaml_env_tag`) instead of guessing from the package name.
- A single report table grouped by verdict (drop / inline / keep), with per-dependency usage counts and a `WHERE` column pointing at the exact file:line for lightly-used dependencies.
- Colored terminal output (auto-detects `NO_COLOR` and non-TTY destinations).
- Prebuilt wheels for Linux (x86_64/aarch64), macOS (universal2), and Windows (x86_64), published via PyPI trusted publishing.

### Validated against
- A real clone of [mkdocs/mkdocs](https://github.com/mkdocs/mkdocs): 15 declared dependencies, 3 flagged to drop (`babel`, `colorama`, `importlib-metadata`), 4 flagged to inline (`markupsafe`, `mergedeep`, `packaging`, `pyyaml-env-tag`), 8 kept.
